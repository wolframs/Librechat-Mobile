## What I found
1. **The active memory system is OptMem, not LibreChat native memory.** `librechat.yaml:35,59-62,84-87` disables native memory and sets both `optmem` and `web` default-on/chat-menu-visible. `web` fetches an address; it is separate from the Tools menu’s Web Search (`librechat.yaml:79-83`). Do not equate a Web Search switch with the `web` connector switch.
2. **Web offers ordinary per-server checkboxes**, under Tools → MCP submenu and the pinnable MCP composer selector. Each row uses configured title or server name, optional description, connection status and a setup/auth action when needed (MCPSubMenu:39-118; MCPServerMenuItem:35-95). These two yaml entries have no friendly title: the rows fall back to `optmem` and `web`. There is no special OptMem privacy or snapshot explanation in these rows.
3. **Web says the tools switches are chat-scoped.** English `client/src/locales/en/translation.json:2902`: “These switches apply only to this chat. A tool must also be available globally before it can be enabled here.” ToolsDropdown:401 uses it as its tooltip. Pin/unpin changes toolbar placement, not default-on policy (MCPSubMenu:78-94; useMCPSelect:93-115).
4. **Web opt-out is not an immediate server save on click.** The selection updater changes its local atom and `ephemeralAgent.mcpOff`; it does not PATCH the conversation (useMCPSelect:194-207; defaultOn:157-169). A chat submission carries the ephemeral agent (useChatFunctions:434,800); backend `client.js:1976` adds normalized `mcpOff` to conversation save options. Thus an unsent web checkbox edit alone cannot arrive on the phone. The durable opt-out is the conversation document’s `mcpOff`, not the browser’s picker cache (schema/convo:390; defaultOn:25-44).
5. **Sent state wins, otherwise the backend reads stored state.** An explicit `[]` turns defaults back on; omitted/unknown `mcpOff` preserves the stored decision. Default-on servers are added to selection unless opted out, and stale selected names cannot defeat an opt-out. An unreadable stored state excludes defaults (packages/api/src/mcp/defaultOn.ts:65-151). Model-spec operator pins are applied afterwards (same file:97-102); this is not a universal override of administrator policy. Saved-agent OptMem uses the same off list (memoryTools:129-181).
6. **Web defaults are server policy plus browser working state.** `defaultOn` is yaml configuration, not an account settings switch. The picker also remembers selections per conversation in localStorage (`LAST_MCP_` prefix) and writes an environment key for new-chat defaults (store/mcp:17-21; useMCPSelect:202-207). Its storage adapter deliberately ignores cross-tab storage events (jotai-utils:46-90). Default-on seeding overlays the chat’s stored off list on that remembered selection (defaultOn:53-63,124-169). No account-wide OptMem/web opt-out UI was found in the inspected paths. The docs describe expiry of picker selections; I did not independently trace that expiry implementation.
7. **Native-memory controls exist in web source, but are a different system.** Tools has a `Memory` checkbox/pinnable badge, gated by write permissions, memory capability and the account’s native preference (ToolsDropdown:74-75; Memory:13-35). Settings → Data controls → Memory offers “Reference saved memories”, described as allowing the assistant to reference/use saved memories (registry:594-602; MemoryToggle:35-37; translation:2228-2229). It writes `{memories: boolean}` to `/api/memories/preferences`, stored as `user.personalization.memories` (route:264-289). This is not `mcpOff`.
8. **Web native-memory management** has a Memories side panel: key/value search, personal/agent partition filter, usage badge, create/edit/delete dialogs, “Use memory” preference and admin role permissions (MemoryPanel:33-254 and its imported card/dialog components). It is permission gated. On this fork native memory is disabled; backend permission initialization forces the native-memory permission set off even for existing roles (permissions:103-113,153-169,269-296). Therefore these are supported source surfaces, not evidence of a visible OptMem settings page on this deployment. OptMem notes are not managed by that native panel.
9. **Mobile already implements the essential per-chat switches.** Its + → Connectors rows and badge use the effective selection, `(picked − defaults) + (defaults − off)`, and toggles change the off set (ConnectorRules:11-17; ConnectorSession:28-65; ComposerToolsSheetContent:293-324). New chats start with empty opt-outs. Requests send `ephemeralAgent.mcpOff`, including `[]`, or omit it while unknown (ConnectorSession:15-17; ChatRequestBuilder:65-79). The first-send handoff retains it (ChatViewModel:965-966). B5’s unchecked-default/no-opt-out defect is already addressed by this fork, as ledger:111 records.
10. **Mobile wording is weaker than web.** The connector page says “Enabled connectors connect when you send a message.” (strings_composer:33). It does not explain that the switches apply only to this chat, nor that `optmem` means memory and `web` means address fetching. Neither inspected web nor mobile connector UI explains that switching OptMem off leaves earlier memory text in the conversation’s prompt.
11. **A saved web opt-out should arrive, with conditions (code inference).** Mobile opens from Room first (ConversationRepositoryImpl:167-171); Room does not store `mcpOff` (core/model Conversation.kt:155). It seeds the picker from the account-keyed DataStore sidecar, then fetches full conversation detail once per process and cached `updatedAt` version (ConversationLoadDelegate:472-511,570; ChatViewModel:682). The fetched `mcpOff` goes to receiveConnectorState, replaces unedited picker state and updates the sidecar (ConnectorSession:38-51). A fresh process/first open with network, or a later open after the list cache learns the newer timestamp, therefore reads the web-saved off list.
12. **That is not live synchronization.** An already-open screen has no connector subscription to web changes. Reopening with the same cached timestamp can skip the detail GET in that process. A local picker edit prevents the fetched state replacing the in-memory choice (ConnectorSession:45-48). A known stale list is explicitly sent and wins server-side (defaultOn:79-81), so the phone can overwrite a newer web decision if it sends before learning it. Do not describe “arrives” as immediate or unconditional.
13. **Offline reopen has a bounded implementation, not new runtime proof.** ConnectorStore:15-28 keeps the last 100 chats under `acct:<account>:mcp_off`; unknown differs from empty. Its existing test checks store reconstruction, account separation and eviction (fork/src/androidUnitTest/kotlin/com/garfiec/librechat/fork/mcp/ConnectorStoreTest.kt:15-27). I read it but did not run it. An offline chat absent from that sidecar retains unknown opt-outs and sends no list; it cannot reconstruct them from Room.
14. **Mobile does not lack native-memory management in general.** It has a Memories settings screen with search, personal/agent partitions, usage, add/edit/delete and an account switch called “Use saved memories” / “Chats can read and save memories” (settings strings:487-518; MemoriesScreen:249-436; MemoryEditSheet:141-205). It uses the same native `/api/memories` and preference APIs (MemoriesApi:39-54). Its permission helpers additionally allow a switch-only page without READ (settings CLAUDE:52-56). These controls do not manage OptMem and should be hidden by this backend’s native permission disablement. Native composer Memory is separately gated (ChatUiState:973-985).
15. **OptMem off is not erasure, on either client.** Backend freezes the original snapshot/rules/tool definitions; later off requests refuse tool execution while keeping those bytes. Turning on after an off start adds tools/rules, not a retroactive snapshot (contextSnapshots:16-57; memory-architecture doc:202-210; memoryTools:38-43). No dedicated OptMem notes browser, account default switch, refresh button or purge page was found in the inspected client surfaces; model tools and offline operator purge are distinct mechanisms.
16. **Upstream since the app check:** `d9afdcc9` (#885) filters chat-hidden/consume-only MCP servers and is already merged. It does not add the backend fork’s `defaultOn`/`mcpOff` contract or improve cross-client refresh. The other relevant hit, `a5a0b7b1` (#883), concerns edited/retried turn positioning. Neither closes the wording gap or proves the two unrun ledger scenarios.

## Verdict
**real gap**, narrowly: mobile lacks web’s explicit per-chat scope wording. The core default-on/opt-out behavior is already implemented. A web opt-out should reach the phone after it has been sent/saved and mobile performs a qualifying detail fetch; immediate cross-client synchronization is not implemented. Missing OptMem management/default settings are shared backend/web limitations, not mobile-only omissions.
