## What I found
1. **The fallback still ignores keys.** The seeder's tiers are 0 explicit route agent/model; 0b prioritized spec; 1 valid last-used; 1b soft spec (then openable specs under enforce); 2 first agent when the active endpoint is agents; 3 first config model. Initial state is `agents` with no model. Thus a fresh install waits for the agent list; an account with agents can stop at tier 2. Without an applicable spec, last-used or agent, tier 3 takes `filtered.entries.firstOrNull()` and that entry's first model (`ModelSelectionDelegate.kt:543–632,702–845`).
2. “Valid” here means listed, not authenticated. `selectability` checks model/agent membership and whether inputs have loaded. `filterModelsByEndpoint` removes agents, empty lists, unconfigured endpoints and duplicate models. Neither checks keys or sorts by `EndpointConfig.order` (`:952–988,1239–1248`). Repository normalization also preserves response order (`ConfigRepositoryImpl.kt:426–427`).
3. **Key information already exists, but arrives separately.** `/api/endpoints` supplies `userProvide`/`userProvideURL`. The config collector starts `EndpointKeyStatusDelegate.recomputeFor` asynchronously. It asks `GET /api/keys?name=<endpoint>` for gated endpoints, with Azure's key-name mapping. The returned expiry means Unset, Set, or Expired; Loading covers the initial request. New fetch failures become Unset, while an established status survives transient errors. No key value is returned or needed (`KeysApi`, `KeyRepositoryImpl`, `EndpointKeyStatusDelegate`, `KeyState`).
4. At the first seeding emission, endpoint config or key results may not have arrived. Even once they do, key state is **not a seeder combine input** and the tier-3 choice never reads it (`ModelSelectionDelegate.kt:547–573`). A later key result therefore cannot correct an already-listed model. The picker does use this state: Unset/Expired block selection; Loading/null fail open (`ModelSearch.kt:51–72`). The fork's usable-first picker grouping only changes display order, not seeding (`ThreadPickerGroups.kt`).
5. **YAML custom order:** Ollama → xAI → Surplus → Surplus (Claude) → OpenRouter (`librechat.yaml:320,332,350,366,436`). Ollama uses a fixed local placeholder key and defaults to `llama3.1`; the other four explicitly use `apiKey: user_provided`. All five fetch model lists. Their fallback lists start with `grok-4.3`, `deepseek-v4-flash`, `claude-opus-4.8`, and `mistralai/mistral-large-latest`, respectively. These defaults are not proof of the current fetched catalogue. There is no `modelSpecs` or `interface` section in this YAML.
6. YAML order is **not the complete endpoint/model order**. Built-ins are configured through environment settings, not those custom rows. Air `env-reference.md:46` documents OpenAI, Anthropic, Google and Assistants as `user_provided`. The backend model response puts built-ins first: OpenAI → Google → Anthropic → Azure OpenAI → Assistants → Azure Assistants → Bedrock, then the custom map (`ModelController.js:6–11`, `loadDefaultModels.js:75–82`); mobile drops disabled/empty entries. Thus putting Ollama first in YAML does not put it before OpenAI in mobile's tier 3.
7. Web endpoint ordering is separate again: absent an `ENDPOINTS` override, configured built-ins follow OpenAI → agents → Assistants → Azure Assistants → Azure OpenAI → Google → Anthropic → Bedrock; unconfigured rows are omitted and custom rows follow. `ENDPOINTS` can override it (`parsers.ts:78–136`, `loadDefaultEConfig.js:13–33`). I did not read credential files or live process environment to assert the effective override today.
8. **Today's code retains the November 13 failure path.** With that check's conditions—no prior selection, no applicable spec/agent, an OpenAI catalogue beginning `gpt-5.5`, and no stored OpenAI key—it still selects OpenAI / `gpt-5.5`. This is a static inference from unchanged selection logic, not a new app run. Today's exact first model string, per-user keys and agent list were not read live. A fresh app install does not erase keys stored for the account on the server.
9. **Official web does not skip missing-key providers either.** With no spec/preset or stored setup, `getDefaultEndpoint` chooses the first configured endpoint in `mapEndpoints` order. `buildDefaultConvo` prefers a valid remembered model, otherwise passes the supplied model order to `parseConvo`. Neither consults key expiry. Specs can override this through `getDefaultModelSpec`/`useNewConvo`. A separate `useRequiresKey` checks the selected endpoint's `userProvide` and `useUserKey` expiry; it does not reroute the chat. On the same no-spec, OpenAI-first configuration, web also lands on OpenAI, subject to its own model catalogue order.
10. **No upstream fix since the check.** The selection-file diff from `08bca78f` to `af0ea66e` contains only #864's agent-list comment changes (`2c03dc97`); the tier-3 choice and inputs are unchanged. The key-status file has no commits in that range. Config repository changes concern account-switch result isolation, not credential-aware ordering. Issue searches found related completed model-spec work (#538, #552, #638) and key plumbing (#70), but no matching fix for this fallback. Search absence is not proof that no differently worded issue exists.

## Verdict
**real gap.** The mobile fallback can still open on a provider known to lack a key. The same November 13 inputs still produce the same bad choice. Official web has the same credential-blind fallback; this is an improvement over that behavior, not missing web parity. “Has a stored key” also cannot guarantee “can answer”: the November check records unusable stored keys and an expired upstream OpenRouter credential despite a stored record.

## Recommended action
**M (a few hours).** Add a credential-aware **tier-3 fallback**, preserving route picks, specs, last-used choices and agent precedence. Use the current endpoint flags plus existing key-state results; choose the first nonempty endpoint requiring no user value or having `KeyState.Set`. Wait for gated candidates' initial status instead of treating absent/Loading as known usable. If none qualify, leave a clear provider-setup path rather than inventing a usable model. Do not probe providers or hardcode Surplus/model names.

Put the plain fallback policy in `fork/src/commonMain/kotlin/com/garfiec/librechat/fork/modelseed/`. Put any bridge requiring chat state/handles in `chat/fork/`, per `fork/README.md` rules 1–2. Add minimal fully-qualified `FORK-HOOK(first-model)` calls at tier 3 and the seeder's input wiring so key resolution re-evaluates that fallback. Merely changing `firstOrNull` without wiring updates can strand the selection, because current valid selections return early. Keep `util/SpecSeed.kt` unchanged: it mirrors upstream, explicitly protected by `feature/chat/CLAUDE.md:80–83`. Register hooks, update the ledger, and put fork policy tests in `fork/src/androidUnitTest` as the fork rules require.

Acceptance should cover the recorded no-last-used/no-agent case with missing OpenAI and a stored Surplus key, delayed key results, no usable endpoint, and preservation of explicit/spec/last-used choices. A stored-but-rejected key remains B2's error/setup concern.
