## What I found
1. **The pre-send guard does not resolve B2.** SendReadinessDelegate refuses a known blocking key state with `ApiKeyRequired`; loading/unknown states pass. That tests the client's metadata, not whether the backend can use a saved record. B2 concerns a record that exists but fails at use time, as the app-check explicitly records.
2. **SSE transport preserves the error payload.** SseLineParser collects `event:` and `data:` until a blank line. SseEventMapper reads the data JSON; a top-level `error` becomes `StreamEvent.Error(message=...)`. Strings are unwrapped; objects/arrays become JSON text. It does not dispatch specifically on the `event: error` name: that frame still needs the expected data envelope. Final/created/sync control handling precedes the ordinary error path. SseClient treats a mapped error as terminal (evidence: mapper:96-178; client:96-116).
3. **The live terminal-error path already recognises five key types.** StreamingManagerDelegate handles `StreamEvent.Error`, ends the run, then calls `parseUserKeyError`. Recognised types: `no_user_key`, `invalid_user_key`, `expired_user_key`, `no_base_url`, `invalid_base_url`. Expired requires `expiredAt`; endpoint is optional and falls back to the turn's endpoint (or the known agent's provider). Unknown types, malformed JSON, prefixed prose, and expired payloads missing `expiredAt` do not parse (UserKeyError:55-75).
4. **A recognised live key error gets a readable snackbar and an action.** It clears the generic error state and emits through ChatViewModel's user-key channel, avoiding a second generic banner. The snackbar says, for example, “No key found for <provider>. Please provide a key and try again.” Invalid says to provide a valid key; expired names the expiry. “Add key” navigates to Provider API Keys, passing the endpoint to open its editor; absent endpoint opens the list. Base-URL errors also use that action (StreamingManagerDelegate:813-852; UserKeyErrorSnackbarEffect:34-46; resources:388,525-536).
5. **The thread takes a different path and still shows raw key JSON.** A persisted `error:true` reply with no content and nonblank text goes through StreamErrorPart; an ERROR content part also goes through it. It calls `StreamErrorType.markerOrText`, then `localizedStreamError`, then ErrorContentPart's red container. StreamErrorType deliberately excludes all user-key types, saying the snackbar handles them. Unknown values return the original string (`markerOrText:416`); localizedStreamError returns unmarked text unchanged (:33). This path never calls parseUserKeyError or userKeyErrorMessage. Its comment about generic unknown handling is not what this implementation does.
6. **Therefore all five types can remain raw in the red reply**, including a fully formed expired payload. This holds for persisted error text and ERROR content parts. It also holds for other unknown structured error codes. The live snackbar can be correct at the same time: after emitting it, endStream reloads the conversation (:853-856), exposing the persisted raw reply. This is a code-derived prediction, not a device reproduction or proof of the exact frame sequence on 13 November.
7. **HTTP start failures are not SSE frames.** ChatRepositoryImpl POSTs first and subscribes to SSE only after success (:127-157). Its retryStart rethrows terminal ApiException. LibreChatHttpClient extracts primitive `message`, `error`, or `error_message` into ApiException, retaining the original body separately. StreamingManagerDelegate's collectStreamSafely runs toSafeError and special start-failure mappings, then the same endStream key parser (:424-447).
8. **HTTP key recognition depends on the envelope and message filter.** A short `{"type":"no_user_key"}` string inside HTTP `error` or `message` survives extraction and toSafeError, then gets the key snackbar. The same is true for short invalid-key/base-URL payload strings. A bare top-level `{type:...}` or object-valued `error` has no extracted primitive message, so gets an HTTP status fallback instead. Server-authored text is filtered before the parser: more than 200 characters, URLs, markup/newlines, or an unspaced string longer than 40 characters becomes generic failure text. A normal compact expired-key JSON with endpoint/date exceeds 40 and has no spaces, so this HTTP path loses its typed mapping. It does not render that long raw object; it loses the helpful expiry/action instead (FailureMessages:95-104; Result:80-93). No full-body key parsing rescues it.
9. **HTTP failure opening the SSE GET is a third case.** SseClient handles status exceptions: 404 ends silently, 401 emits “Unauthorized”, other statuses retry then emit an HTTP-status sentence/reconcile code. It does not extract a key payload from that response body (:155-203).
10. **A record's existence is not its usability.** On the Air, getUserKey throws no_user_key if no matching record exists, but custom initialization also throws it when the retrieved values have no usable `apiKey` (:276-280). getUserKeyValues throws invalid_user_key when decrypted values fail JSON parsing (:66-75). Expiry throws expired_user_key with endpoint and ISO expiredAt. Thus the reported type need not mean “no record”. The official pin uses decryptStoredKey where the Air uses decrypt; I did not assume identical decryption failure behavior. No historical key values were read.
11. **Official web maps the errors in the reply itself.** Its Error component extracts JSON (including embedded JSON), selects code/type, supports a nested error envelope, and dispatches through registry to UserKeyError. That renderer covers all five types and degrades expiry without expiredAt to invalid-key wording. It resolves endpoint ownership before offering an editor (official index:49-80; registry:53-57; UserKeyError:71-160).
12. Official English user-owned copy is “Add your own {{0}} API key to send messages.”; “The {{0}} API key you saved could not be read. Update it and try again.”; “Your {{0}} API key expired on {{1}}.” Generic no-key wording is “An API key is required to send messages.” Admin-owned no-key wording asks an administrator to add one. Missing URL asks to add it; rejected URL asks for a valid external HTTP/HTTPS address. The reply offers “Add your key”, “Update your key”, “Add your URL”, or “Update your URL”, only when the reader can edit that endpoint. The Air's inspected renderer and matching translations use these same key-error sentences; this is source parity, not deployed browser verification.
13. **No upstream mobile fix since 13 November.** The relevant parser, localized text mapper, ERROR-part and persisted-error rendering files have no changes in `08bca78f..af0ea66e`; neither does the HTTP extraction/filter. StreamingManagerDelegate changed for queue/OAuth work, not this key mapping. The typed key parser's last change was `dad052d2` on 27 October (#669), so its snackbar support predates the reported bug. Searches found older closed [#70](https://github.com/garfiec/Librechat-Mobile/issues/70) covering provider-key setup and live error mapping, and unrelated auth-error reports; no matching open/closed report for the remaining raw key-error reply was found. Search absence is not proof none exists.

## Verdict
**real gap.** Today's code can still show the reported raw no_user_key object in a persisted failed reply or ERROR content part, and likewise invalid_user_key, expired_user_key and both base-URL types. Live snackbar handling already exists. HTTP handling has separate envelope/filter limitations. No relevant mobile upstream fix was found since 13 November.
